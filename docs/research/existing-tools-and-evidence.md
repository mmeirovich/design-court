# No mature tool closes Crucible's loop

> Note: this report was written when the plugin was still called "Crucible". It has since been renamed Design Court, because other Claude Code plugins already use the name Crucible.

No. As of November 2026, no mature, widely adopted and well-tested tool runs the full loop Crucible implements on designs, specs or plans. That loop has blind independent reviewers, cross-examination between them, an evidence-based judge, automatic fixes, rounds until convergence, and human questions limited to product decisions. Adoption and completeness run in opposite directions. The heavily used tools each implement one or two pieces: Superpowers (about **1.0M installs**), GitHub Spec Kit (**149k stars**), BMAD-METHOD (**55k stars**), Compound Engineering (**26k stars**) and OpenAI's codex-plugin-cc (**35k stars**). The tools that implement most of the loop are small, single-maintainer projects only months old, and none has a quality benchmark. Examples are agent-review-panel (**37 stars**), adversarial-spec (**558 stars**, dormant since January 2026), metaswarm (**428 stars**) and convergo (**9 stars**). The research evidence is also unfavourable to Crucible's most distinctive feature. Compute-matched studies find that most gains credited to multi-agent debate come from simple voting over independent samples. Debate often flips correct answers to wrong ones, and the best-documented production reviewers (Cursor Bugbot, Anthropic Code Review) use independent passes plus a verifier, not debate. Crucible fills a real gap, then, but it is unproven, and its debate-and-converge machinery is the part the evidence supports least. You should keep Crucible, borrow specific mechanisms from five or six existing tools, and benchmark it against a budget-matched "independent reviewers plus verifier" baseline before trusting its debate rounds.

## Adoption and loop completeness run in opposite directions

The landscape splits into three tiers. The first is mass-adoption workflow frameworks that contain a review step but no adversarial loop. The second is vendor review products that are mature but review only code diffs. The third is a long tail of community plugins that implement most of the target loop but have little use and no outside validation. The table below compares the closest candidates on the seven elements of the target workflow. Adoption figures are GitHub stars or published install counts, pulled on 2026-11-10.

Anthropic's own offerings fill in the code side but not the design side. The managed Code Review service and ultrareview both run "find → verify → rank" pipelines. Every finding is "independently reproduced and verified", but they review **code diffs only** and run a single pass ([Ultrareview docs](https://code.claude.com/docs/en/ultrareview); [Code Review docs](https://code.claude.com/docs/en/code-review)). `/code-review --fix` applies findings once, with no re-review ([docs](https://code.claude.com/docs/en/code-review-local)). The official feature-dev plugin does run 2–3 parallel architect agents, but it makes the human pick an architecture and triage every review finding, which is the opposite of "product questions only" ([feature-dev.md](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/feature-dev/commands/feature-dev.md)). **Ultraplan, the one built-in cloud plan-review feature, was removed on 2026-08-04** in favour of plan mode with human approval ([Ultraplan page](https://code.claude.com/docs/en/ultraplan)). The building blocks exist. Dynamic workflows explicitly suggest having "independent agents adversarially review each other's findings" or "draft a plan from several angles and weigh them against each other" ([Workflows docs](https://code.claude.com/docs/en/workflows)), and agent teams, still experimental, prescribe a "competing hypotheses" debate ([Agent teams docs](https://code.claude.com/docs/en/agent-teams)). Nobody packages them as a design-review loop.

Other ecosystems repeat the pattern. Kiro's Analyze Requirements finds contradictions in requirements and streams clarifying questions with suggested fixes, which it writes back to the spec. That is the closest vendor match to product-only questioning, but it is a single analysis engine that stops before design ([Kiro docs](https://kiro.dev/docs/specs/analyze-requirements/)). Karpathy's llm-council (26k stars) has the cleanest "independent answers → anonymized peer ranking → chairman" design, but its author calls it a "Saturday hack" he will not support ([README](https://github.com/karpathy/llm-council)). PAL MCP's `consensus` tool assigns for, against and neutral stances across models, but it has had no push since December 2025 ([PAL](https://github.com/BeehiveInnovations/pal-mcp-server)). AutoGen, CrewAI, LangGraph and MetaGPT can all express debate, but they ship it only as generic math-benchmark examples ([AutoGen debate pattern](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/design-patterns/multi-agent-debate.html)).

The fit verdict is that no tool is a drop-in replacement for Crucible. agent-review-panel is the closest *architecturally* (blind reviewers, debate, judge, verification), ce-doc-review and Superpowers are the closest *operationally* (auto-applied corrections, product-only questions, real adoption), and adversarial-spec, metaswarm and convergo are the closest on the *loop*. Real-world testing is thin everywhere: one HN commenter on a similar tool summed up the space as "nobody is doing real testing or benchmarks" ([HN](https://news.ycombinator.com/item?id=48090276)).

## Debate adds little beyond voting; verification does the work

The academic record has turned against multi-agent debate as a mechanism. Early papers reported gains, but compute-matched re-evaluations attribute those gains to ensembling. Choi, Zhu and Li (NeurIPS 2025) conclude that **"Majority Voting alone accounts for most of the performance gains typically attributed to MAD."** With Llama-3.1-8B, majority voting reached 0.724 against 0.699 for the best debate variant and 0.620 for a single agent. They model debate as a martingale, meaning an agent's expected belief in the right answer stays flat across rounds unless the updates are biased toward correctness ([arXiv 2508.17536](https://arxiv.org/html/2508.17536v1)). An ICLR 2025 blogpost tested five debate frameworks on nine benchmarks. On HumanEval, Du et al.'s debate scored **68.09 against 78.05 for plain chain-of-thought**, and adding agents or rounds "did not reliably improve accuracy", while self-consistency did scale with tokens ([ICLR Blogposts](https://d2jud02ci9yv69.cloudfront.net/2025-04-28-mad-159/blog/mad/)). Wynn et al. found that flips from correct to incorrect outnumbered the reverse and that the gap widened in later rounds. Three Mistral agents on MMLU fell from 33.6% to 24.4% ([arXiv 2509.05396](https://arxiv.org/html/2509.05396v2)). A 2026 AWS preprint measured debate minus voting at a matched budget and got results from **−22.6 to +4.6 points**. It also found that a single self-critique prompt flipped 100% of unanimous answers ([arXiv 2605.09618](https://arxiv.org/pdf/2605.09618)). Debate does help when it adds information the agents did not share, such as heterogeneous models, diverse roles or a correctness signal. That is the condition Crucible has to satisfy.

Evidence from code review points the same way. On SWR-Bench (FSE 2026), running a reviewer several times and merging the reports **raised F1 by up to 43.67%**, which is direct evidence for independent-sample aggregation in review ([arXiv 2509.01494](https://arxiv.org/html/2509.01494v2)). Cursor's Bugbot launched with eight parallel passes in randomized diff order, majority voting and a validator model. It later reached its largest gains by moving to a single agentic reviewer, and its resolution rate rose from 52% to over 70% ([Cursor](https://cursor.com/blog/building-bugbot)). Anthropic's Code Review runs parallel finders followed by a verification step, and reports **fewer than 1% of findings marked incorrect** at about $15–25 per PR ([claude.com blog](https://claude.com/blog/code-review)). Neither production system describes reviewers debating each other. The one quantified cost-benefit comparison found came from Quickchat's benchmark of Claude Code review. A multi-agent max review found **23 of 27 serious bugs for $21 in 56 minutes**, while a single-agent high review found **21 of 27 for $0.11 in 40 seconds** ([Quickchat](https://quickchat.ai/post/claude-code-multi-agent-code-review); [HN](https://news.ycombinator.com/item?id=50182359)).

The judge is a second weak point when every agent is the same model. LLM judges prefer their own generations, and the bias is linked to lower perplexity on familiar text ([Wataoka et al.](https://arxiv.org/pdf/2410.21819); [Panickssery et al.](https://arxiv.org/abs/2404.13076)). Position bias was strongest on software-development tasks, and Claude-3 judges consistently favoured the later answer. All nine judges tested agreed on only **23.4%** of instances, and same-family judges agreed with each other more often, a sign of shared biases ([Shi et al.](https://arxiv.org/html/2406.07791v1)). Judges are least consistent when candidates are close in quality, and in review that means exactly the "real issue or nit?" calls a Crucible judge exists to make. agent-review-panel's own README concedes the core problem: same-model panels are **"structured *self-critique*, not independent verification."** ([README](https://github.com/wan-huiyan/agent-review-panel)).

Critique loops help when they are grounded. Self-correction without external feedback often fails or degrades answers ([Huang et al.](https://arxiv.org/pdf/2310.01798)). It works with reliable external signals such as tools, execution or a stronger model ([Kamoi et al.](https://arxiv.org/abs/2406.01297); [CRITIC](https://arxiv.org/abs/2305.11738)). The evidence is not all negative, though. On CR-Bench-v2, a Reflexion-style self-reflection loop improved defect detection for every backbone, by up to **+12.6 points**, but extra cost was not counted ([arXiv 2611.02566](https://arxiv.org/html/2611.02566v1)). Anthropic's harness-design post found that **separating the generator from a skeptical evaluator "proves to be a strong lever,"** but also that scores plateaued and "I regularly saw cases where I preferred a middle iteration over the last one" ([Anthropic Engineering](https://www.anthropic.com/engineering/harness-design-long-running-apps)). The honest caveat is that **no study tests debate on software design review specifically**. Design review is an open-ended search for issues, not single-answer QA. That favours diversity and recall, which argues for a union of independent findings followed by verification, not for debating toward consensus.

## Four forces explain why no mature equivalent exists

The first force is that the core mechanism is unproven. A product built around debate cannot point to evidence that debate beats a cheaper ensemble, and the vendors with the most data have chosen ensembling plus verification. The second is that absolute accuracy is still low and ground truth is noisy, worst of all for design. The best SWR-Bench F1 is about **19–21%**, most tools have precision under 10%, and design and evolvability issues score worse than logic bugs (best **16.45%** F1) ([SWR-Bench](https://arxiv.org/html/2509.01494v2)). Human raters agree on what counts as a valid review comment only 0.48–0.75 of the time ([CR-Bench-v2](https://arxiv.org/html/2611.02566v1)), and no benchmark for design or architecture review exists at all. A tool cannot become "well-tested" in a domain that has no test set.

The third force is cost. Anthropic reports multi-agent systems use **about 15x the tokens of chat**, and that token spend alone explains about 80% of performance variance on BrowseComp ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). That is a warning that multi-agent "wins" can come from spending more. agent-review-panel self-reports **$3–$20 per run**, and one audited full run cost **$162**, with **69% of the cost in the orchestrator loop** rather than the reviewers ([README](https://github.com/wan-huiyan/agent-review-panel)). By comparison, a single-agent PR bot in an industrial study cost about $0.48 per PR ([Cihan et al.](https://arxiv.org/html/2412.18531v2)).

The fourth force is that prompt-orchestrated loops are fragile. agent-review-panel's own issues document the orchestrator **"silently skips Phase 4 (reflection), 5 (debate), 7 (blind final)"** under context pressure, and a Supreme Judge that "can introduce hallucinated P0s" ([issues](https://github.com/wan-huiyan/agent-review-panel/issues)). convergo was built because plan-review loops "often [don't] converge — each round adds patches, prose, and pseudo-code", making the artifact "larger, vaguer" ([convergo](https://github.com/gomilesf/convergo)). Practitioners report scope creep over "5 to 8 loops" and note that "prompt based orchestration is non-idempotent" ([HN](https://news.ycombinator.com/item?id=48090276)). Anthropic's best practices warn that "a reviewer that's asked to find problems will always find *something*. If you fix every finding, you end up with extra abstraction layers" ([Best practices](https://code.claude.com/docs/en/best-practices)).

Vendors are also simplifying. Ultraplan was removed, and `/code-review` switched to "leaner inline review prompts... instead of spawning many review subagents" for untuned models ([Changelog](https://code.claude.com/docs/en/changelog)). The steelman for Crucible's direction is that the platform primitives (workflows, agent teams) only arrived in 2026, and demand is visible. The most-reacted issue on codex-plugin-cc is a request to "Review Plan" ([issues](https://github.com/openai/codex-plugin-cc/issues)). The gap is partly a matter of timing, not proof that the idea fails.

## What to do with Crucible: borrow, benchmark, then simplify

**Borrow before you rebuild.** Six tools contain mechanisms that patch Crucible's known risks:

- **agent-review-panel**: sycophancy detection when more than 50% of position changes lack new evidence, a correlated-bias warning when all reviewers converge, a post-judge verification gate, and a loud `[NO-DEBATE]` banner when phases are skipped ([README](https://github.com/wan-huiyan/agent-review-panel)). These map directly onto Crucible's cross-examination and judge.
- **ce-doc-review**: auto-applies only *proven* corrections. When a finding comes from only one model, it has a reviewer re-check it blind, without that model's claims ([guide](https://github.com/EveryInc/compound-engineering-plugin/blob/main/docs/guides/ce-doc-review.md)). That is a sound gate in front of Crucible's editor.
- **Superpowers' builder check**: sorts questions into "answered already", "settle it yourself" and "theirs", and runs "only one round of questions" ([SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)). Version 7.0.2 cut filler questions from 41 to 23 in blind-graded tests ([release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)). This is a tested template for Crucible's product-only routing.
- **convergo**: fresh reviewer sessions per round and a hard stop after three repair rounds that leave blockers unresolved ([README](https://github.com/gomilesf/convergo)).
- **claude-security**: verifiers are told to call a finding a false positive unless they can confirm it. Severity is capped by the number of confirming verifiers, and the verification record is "computed in code" ([README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/claude-security/README.md)).
- **math-olympiad**: a "context-isolated" verifier that "sees only the clean proof, never the reasoning trace" ([README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/math-olympiad/README.md)). That is the right model for Crucible's fresh judge.

For cross-vendor diversity, `/codex:adversarial-review` or PAL's `consensus` can supply a non-Claude reviewer or judge. Expect integration fragility, such as codex-plugin-cc's open issues about stuck reviews and orphaned processes ([issues](https://github.com/openai/codex-plugin-cc/issues)). Run each of these tools once on a real design doc of yours before or alongside Crucible. That is the cheapest way to calibrate expectations.

**Benchmark against a budget-matched baseline.** Take riekelt's approach and build a small corpus: 10–20 real design docs and plans with planted defects, plus past designs whose real problems surfaced later in implementation, which gives you ground truth after the fact ([riekelt](https://github.com/riekelt/multi-agent-review)). Run four arms, each three times to measure variance:

- **A**: one fresh-context reviewer.
- **B**: N blind reviewers, then union and dedupe, then an evidence-checking verifier and editor, at the *same token budget* as Crucible. This is the Bugbot and Anthropic Code Review pattern.
- **C**: full Crucible.
- **D**: Crucible with cross-examination and rebuttal removed.

Score every arm with the same judge, ideally from a different model family plus a blind human spot-check, because judges differ in calibration ([CR-Bench-v2](https://arxiv.org/html/2611.02566v1)). Track these metrics:

- planted-defect recall;
- false-positive rate;
- true findings dropped between rounds (the flip rate);
- document growth per round (scope creep);
- the share of human questions that are genuinely product questions;
- tokens, dollars and wall time.

The decision rule is simple. Keep cross-examination and rebuttal only if C clearly beats both B and D at equal cost. If B ≈ C, the debate layer is buying conformity risk and cost for nothing. Implementing the orchestration as a dynamic workflow script rather than a prompt also makes runs reproducible and prevents silent phase-skipping. Workflows support exactly this kind of scripted fan-out and stop rule ([Workflows](https://code.claude.com/docs/en/workflows)).

**Where the evidence supports or questions Crucible's design choices:**

| Crucible choice | Evidence verdict | Concrete change |
|---|---|---|
| Blind independent reviewers | **Supported**: voting and independent samples carry most gains ([Choi et al.](https://arxiv.org/html/2508.17536v1); [SWR-Bench](https://arxiv.org/html/2509.01494v2)) | Keep; give each reviewer a distinct lens, since persona diversity was essential in ChatEval ([arXiv](https://arxiv.org/abs/2308.07201)) |
| Anonymized cross-examination | **Questioned**: interaction causes correct→wrong flips ([Wynn et al.](https://arxiv.org/html/2509.05396v2)); anonymization is plausible but untested | Restrict to evidence-backed refutation of specific findings; log and measure flips |
| Rebuttal round | **Weak**: verbosity bias rewards the longer argument ([Zheng et al.](https://arxiv.org/abs/2306.05685)) | Require rebuttals to cite spec sections or code locations; judge the evidence, not the prose |
| Fresh judge each round | **Partly supported**: context isolation helps ([harness post](https://www.anthropic.com/engineering/harness-design-long-running-apps)), but same-family self-preference persists ([Wataoka et al.](https://arxiv.org/pdf/2410.21819)) | Use a different model family as judge or a cross-family vote; swap finding order |
| Editor auto-applies fixes | **Supported if gated**: over-fixing is a documented failure ([Best practices](https://code.claude.com/docs/en/best-practices)) | Apply only judge-verified blockers and majors; add a diff or regression check after each edit |
| Verification rounds | **Supported when grounded** ([Kamoi et al.](https://arxiv.org/abs/2406.01297)) | Give verifiers read and grep access to the codebase so design claims are checked against reality |
| Loop until convergence | **Questioned**: agreement is what conformity produces; middle iterations sometimes beat the last ([harness post](https://www.anthropic.com/engineering/harness-design-long-running-apps)) | Cap at 2–3 rounds; stop when a round yields no new evidence-backed blocker; abort if the document keeps growing |
| Product-only human questions | **Supported by practice**, not by controlled studies ([Superpowers](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md); [Spec Kit](https://github.github.io/spec-kit/reference/agentic-sdd.html)) | Keep; batch into one round of at most five questions, as Spec Kit's `/clarify` does |
| Same model everywhere | **Questioned**: shared-family bias ([Shi et al.](https://arxiv.org/html/2406.07791v1)); mixed models often helped debate ([ICLR blog](https://d2jud02ci9yv69.cloudfront.net/2025-04-28-mad-159/blog/mad/)) | Put at least one non-Claude reviewer and/or the judge on Codex or Gemini |
| Cost | Comparable tools run **$3–$162** per run, with the orchestrator dominating ([agent-review-panel](https://github.com/wan-huiyan/agent-review-panel)) | Instrument tokens per phase; offer a "budget" mode (arm B) as the default and full debate as opt-in |

## Conclusion

Crucible's real novelty is probably not where it looks. The debate-and-cross-examination layer is the most contested part of the design, and it is the layer that mature vendors have avoided. The less glamorous combination is what nobody ships at scale: blind reviewers on *design documents*, evidence-verified fixes applied without human triage, and question routing that sends the human only decisions about product intent. That gap is real and has visible demand. Frame Crucible as a design-review harness with grounded verification and product-only escalation, and treat debate as an ablation to be earned, not a premise.

Building your own benchmark is the more durable contribution. Even a small planted-defect corpus with budget-matched arms would make Crucible one of the few tools in this space with evidence, since most competitors, including agent-review-panel, openly say they have none. If the numbers show that independent reviewers plus a cross-family verifier match the full loop, you get the same quality for a fraction of the cost and with fewer failure modes. If debate does win on design docs, which no published study has tested, you will have found something the literature has not.
